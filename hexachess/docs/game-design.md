### 命名研究结论（基于微信小游戏 ASO 规律检索）

- **名字占搜索排名权重约 35%**，且应把用户常搜的「品类词」前置。

## 1. 项目定位

### 1.1 一句话核心玩法

> **拖一个棋子进任意空格，与相邻同色自动合并叠高，叠满 10 个消除；棋盘被沾满且无法消除 → 失败；凑齐 6 色各消除 1 →「将杀」。**

### 1.2 目标用户

- 主力：18–35 岁、碎片化时间多的休闲玩家（地铁、睡前）。
- 次主力：轻度棋类爱好者（被「国际象棋」皮肤吸引，但不需要真会下棋）。
- **不**面向：硬核策略玩家、竞技对战玩家。

### 1.3 设计原则（铁律）

| 原则    | 说明                                     |
| ----- | -------------------------------------- |
| 单手可玩  | 全程竖屏、单指拖拽，不依赖双手或横屏。                    |
| 3 秒上手 | 开局即给一个已接近完成的容器，玩家立刻理解「同色装进去」。          |
| 无失败焦虑 | 不做硬性「Game Over」，卡关可重开/换布局，保持轻松。        |
| 零付费墙  | MVP 阶段**完全免费 + 纯广告变现**，不开任何内购（见第 6 章）。 |
| 棋味不硬核 | 国际象棋只做「视觉身份 + 轻量目标包装」，不要求玩家懂走法。        |
| 家长友好  | 无内购、单机关卡、无陌生人聊天；定位益智解谜，易被家长接受为放心游戏     |

### 1.4 明确不做的范围（MVP 阶段）

- ❌ 真人实时对战 / 联机（会触发版号，且无服务端成本承受力）。
- ❌ 内购、皮肤付费、体力付费（个人主体无法开通，且触发版号）。
- ❌ 完整国际象棋规则对弈。
- ❌ 横屏模式（首版只做竖屏）。

## 2. 核心玩法

采用 **「方案 A：Hexa Sort 内核 + 轻棋味包装」** 作为 MVP 主线；`方案 B（棋子按国际象棋走法受约束移动）`作为 1.0 后的差异化迭代。

### 2.1 玩家幻想与一句话玩法

- **玩家幻想**：你是棋阵的「调度官」，把散落的六色棋子排进空六边形棋盘——同色相邻自动合并飞过去，叠满 10 即「将杀」级消除，集齐六色触发「Checkmate!」全屏彩蛋。
- **一句话**：拖一个棋子进任意空格，与相邻同色自动合并叠高，**叠满 10 个消除**；棋盘被沾满且无法消除 → 失败重开；凑齐 6 色各消除 1 →「将杀」。

### 2.2 M1 已验证基准（后续开发的根）

M1 技术原型已落地并单测全绿（63/0），它验证的不是「完整玩法」，而是**手感与核心闭环**。后续所有设计都建立在这个已验证的根上：

| 维度 | M1 实际实现 | 说明 |
| -- | -- | -- |
| 模型 | 托盘(tray) + 容器(container) | 底部托盘放散子，棋盘排布彩色「将营」容器 |
| 操作 | 拖同色子 → 对应容器 | 跟手、松手吸附/回弹、装入 |
| 消除 | 容器装满 → 消除 + 计分 + 粒子 | 满分反馈闭环 |
| 棋味 | 集齐 6 色各消除 1 次 → 「将杀」全屏彩蛋 | 成就/彩蛋，非强制 |
| 死局控制 | 生成器 70% 刷「所需色」 | 降低死局概率 |
| 关卡 | 6 个手工关（`levels.ts`） | 仅验证递进 |
| 双端 | 微信 `game.js` + 浏览器 `web.js` | 免 AppID 试玩 |
| 单测 | Node 逻辑单测 80/0（M3-K 顶层合并+旋转视角） | 空格放置/整组落入/顶层连通合并/整摞迁移/单格10消除/满格失败/混色组/救援/四机制/旋转互逆 |

**明确差距（M1 → 完整设计）**：① 棋盘并非真六边形蜂窝，容器以网格圆形排布；② 无「在棋盘上暂存 / 同色堆叠」机制（仅托盘直送容器）；③ 关卡靠手工 6 关，未驱动化；④ 无存档 / 撤销 / 提示 / 洗牌救援；⑤ 无连击与星级；⑥ 无新手引导。这些已在 M2 / M3-B 补齐（见 §3.13）。

### 2.3 完整核心循环（Core Loop，Hexa Sort 正确版 · M3-F 重构）

> **方向修正（2026-08-19）**：之前的"将营容器"模型是另一品类。真正的 Hexa Sort 内核是 **空六边形棋盘 + 同色相邻自动合并 + 累满 10 消除 + 满格失败**。本节是 M3-F 重构后的唯一权威依据。

```
[托盘 3 组堆叠（每组 3–6 子，纯随机、可混色）]
   → [玩家拖一"组"（一摞）棋子]
   → [松手 → 落点判定]
        ├─ 空格（cell.stack.length === 0）→ 整组落入（成为该格一摞）
        │     └─ 立刻按"颜色"做连通分量合并判定：
        │         对每个出现的颜色，沿几何相邻 flood-fill 找同色连通块
        │         → 非锚格的同色棋子一个一个 lerp 飞向锚格叠高（逐色飞叠动画）
        │         → 某色连通块累计 ≥ 10 →【消除】（粒子+屏震+分+格子腾空）
        ├─ 非空格 → 弹回托盘（不叠加在已有格子上）
        └─ 出框   → 弹回托盘
   → [消除腾空格 → 又可放新组]
   ↺ 全部格子被占满（无空可放）→ 【失败 FAIL】→ 重开本关
   → [消除次数 ≥ goal] → 通关结算（星级） + 凑齐 6 色 →「将杀」彩蛋
```

**与之前"将营容器"模型的本质差异**：
- ❌ 旧：格子带预设颜色（"红将营只接红子"），子放进去就锁定 → 这是别的品类。
- ✅ 新：格子**完全无颜色预设**，任何颜色都能放；同色合并靠**几何相邻**触发，靠**累满 10** 消除。
- ✅ 新：支持**链式合并**（A→B→C 一路同色飞过去），是 Hexa Sort 的核心爽点。
- ✅ 新：真正的**失败态**——满格且无可消除可能 → 失败遮罩（区别于旧模型的"死局=救援提示"）。

### 2.4 关卡目标与通关 / 失败判定

每关由数据驱动（见 §3.9 Schema），关键字段：

- **boardRadius R**：棋盘六边形半径（R=1→**7 格**，R=2→**19 格**）。棋盘**完全无颜色预设**——任何颜色都能放进任何空格。
- **goal**：本关需达成的**消除次数**（一次消除 = 一叠凑满 10 个被消除）。`clearedTotal ≥ goal` 即过关。
- **activeColors K**：托盘**生成**色数（3→6 渐进），决定本关出现哪几种颜色（板仍接受任意色）。
- **traySlots**：底部固定 **3 组**堆叠（每组是已叠好的一摞棋子，纯随机、可混色）。
- **groupMin / groupMax**：每组棋子数的随机区间（如 3..6），整组拖入空格成为该格一摞。
- **消除阈值 `ELIMINATE_AT = 10`**：某色**连通块**累计凑满 10 触发消除（棋盘格可混色堆叠，按颜色分别连通）。这是 Hexa Sort 的招牌数字。
- **通关**：`clearedTotal ≥ goal` → 结算页（星级）。
- **失败**：所有 `cells.stack.length > 0`（满格无空可放）→ `over='fail'` → 失败遮罩（"格满失败，重开本关"），重开本关不计入战绩。
- **将杀彩蛋**：单关内集齐 6 色各消除 ≥1 → 全屏 CHECKMATE（金闪 + 字样 + 奖励分）。

### 2.5 「将杀」包装（棋味与成就）

- **触发**：单关内集齐全部 active 颜色、且每种至少被消除 1 次 → 触发「Checkmate!」全屏金色闪光 + 字样缩放入场 + 奖励分。
- **性质**：成就 / 彩蛋，非强制；即便不触发也能通关，保证休闲玩家不焦虑。
- **进阶（可选）**：`active=6` 时称「将杀」，`active<6` 时称「小将收官」，文案与奖励档位区分。

### 2.6 难度曲线（参数化，详见 §3.10 与 `src/data/levels.ts`，M3-F 重构）

> 无"将营数/容量 C"概念了。棋盘格子数由 `boardRadius` 决定，难度靠**格子数 + 目标消除次数 + 生成色集 + 托盘槽数**四维递进。

| 阶段 | 关卡段 | boardRadius | 格子数 | activeColors | goal | traySlots（组） |
| -- | -- | -- | -- | -- | -- | -- |
| 教学 | 1–3 | 2 | 19 | 3 | 3 | 3 |
| 成长 | 4–20 | 3 | 37 | 4 | 4→6 | 3 |
| 进阶 | 21–40 | 4 | 61 | 5 | 7→10 | 3 |
| 挑战 | 41–50 | 4 | 61 | 6 | 11→12 | 3 |

> `goal = i<=5 ? 3 : 3 + floor((i-1)/5)`；`groupMin=3, groupMax = i<=10 ? 5 : 6`；托盘固定 **3 组堆叠**，每组棋子纯随机、可混色。

> **进阶机制**（`mechanics: string[]`，**M3-J 已全部接入玩法**，随关卡解锁）：第 8 关起 `lockedCell` 锁格 / 第 14 关起 `decoy` 诱饵子 / 第 21 关起 `timed` 限时 / 第 31 关起 `movingObstacle` 移动障碍（详见 §3.10）。

## 3. 游戏机制详述（实现规格）

> 本章是开发实现的直接依据。所有数值、状态、规则均以「可落地」为准；与 M1 已有实现的差异在 §3.13 汇总。

### 3.1 六边形网格与棋盘（M3-F 重构 · 正确 Hexa Sort）

- **坐标系**：axial 坐标 `(q, r)`（立方坐标 `(x=q, z=r, y=-x-z)` 用于取整）。
- **朝向**：flat-top（平顶），贴合「棋子落格」视觉。
- **像素换算**（flat-top，`size` = 六边形中心到顶点距离）：
  - `x = size * 3/2 * q`
  - `y = size * sqrt(3) * (r + q/2)`
  - 逆运算 `pixelToAxial` 后用 **cube round** 取整，保证落在合法格。
- **棋盘 = 全部空格子**（M3-F 关键修正）：
  - **无颜色预设**：所有格子初始 stack=null，**任意颜色**的棋子都能放进任何空格。
  - **消除与格子无关**：靠"同色叠满 10"消除，与格子身份无关。
  - 半径 `boardRadius` 决定格子数：R=1→7 格（教学），R=2→19 格（成长起）。
- **几何邻接**：两格相邻 ↔ axial 距离 = 1（`hexDistance(a,b) === 1`），共 6 邻居。合并判定只看几何邻接。

### 3.2 棋子（Tile / Group）模型（M3-F+ · 托盘为堆叠组）

**棋盘上的单片（Tile）**——逻辑轻量，只关心颜色（type 由颜色派生）：
| 字段 | 类型 | 说明 |
| -- | -- | -- |
| `color` | string | 6 色之一（见 §4.2 色板） |
| `type`  | string | 与 color 1:1 绑定的棋子名（兵/马/象/车/后/王） |

**托盘组（Group，底部固定 3 组）**——一组**已叠好的一摞棋子**，整组被拖拽：
| 字段 | 类型 | 说明 |
| -- | -- | -- |
| `id` | number | 唯一序号 |
| `tiles` | `Tile[]` | 这一组的棋子栈（底→顶）；**纯随机生成，可混色**（如 红红红红红 / 红红绿绿绿蓝 / 蓝蓝绿绿） |
| `x,y` / `tx,ty` | number | 当前坐标 / 动画目标坐标（整组跟随手指，棋子向上堆叠渲染） |
| `slot` / `scale` / `targetScale` | | 槽位与缩放 |

**格内叠（Cell.stack: Tile[]）**：底→顶存放；**可混色**（一格内可同时存在多种颜色，按颜色分别连通）；堆叠时**视觉上每个 tile 是独立的有高饼**（不要融成一坨）。

> **认知减负铁律**：颜色 ↔ 棋子类型 **1:1 绑定**（红=兵、蓝=马…）。玩家只需看颜色，棋子图标是「皮肤」，绝不出现同色不同型或同型不同色。

### 3.3 棋盘格（Cell）模型（M3-F · 无颜色预设）

| 字段 | 说明 |
| -- | -- |
| `q, r` | axial 坐标 |
| `x, y, r` | 像素（center + radius） |
| `stack` | `Tile[]`：该格的棋子叠（底→顶）；**空数组 `[]` = 空**（无颜色预设） |
| `clearing` | bool：该格是否处于消除动画中（占位但视觉腾空中） |
| `highlight` | 反馈高亮 0..1（合并/落子/消除时脉冲） |
| `mergedAway` | bool：该格是否正在被合并飞走（用于视觉幽灵化） |

**核心规则**：
- 初始所有格 `stack = []`、无颜色。
- 任意颜色的棋子都能放进**任意空格**——无颜色预设；一组棋子整摞落入即成该格一叠。
- 格消除（stack=[]）后**立即**可重新放子，无需冷却。
- 消除判定只看**顶层同色几何邻接**（合并收拢）+ **单格同色累计 ≥ 10**（消除），与格子身份无关；格内可混色，埋藏色随整摞迁移。

### 3.4 拖拽与落点状态机（M3-K · Hexa Sort 正确版 + 旋转视角）

```
IDLE ──pointerdown(命中hitR)──▶ DRAGGING
DRAGGING ──pointermove──▶ 跟随(偏移 + 抬起30px + 放大1.15 + 投影)
DRAGGING ──pointerup──▶ 解析落点:
    指针屏幕坐标 → screenToBoard()（逆视角变换）→ 棋盘平面坐标
    最近目标 = argmin dist(指针, 候选)   候选 = 所有棋盘格(acceptR内)
    if 目标格.stack.length === 0 且未锁且无障碍 → PLACE(整组落入) → 触发顶层连通合并判定
    if 目标格.stack.length > 0 / 锁格 / 障碍   → BOUNCE(弹回托盘，不叠加)
    if 无候选 / 出框                           → BOUNCE

IDLE ──pointerdown(空白处，非按钮非托盘组)──▶ ROTATING
ROTATING ──pointermove──▶ viewAngle += dx × 0.008 rad（跟手旋转棋盘）
ROTATING ──pointerup──▶ 保持当前视角（合并动画期间也允许旋转，纯视图操作）
```

**手感数值（与 §4.4 动效联动）**：
- 命中半径 `hitR = pieceR * 1.15`（防误触，略大于绘制尺寸）。
- 接受半径 `acceptR = cellR * 1.25`（落点略宽容，避免「点在格上却弹回」）；命中判定在**棋盘平面坐标**（已逆变换）中进行，旋转/俯角不影响准确度。
- 拖起抬起量 `lift = 30px`；放大 `scale = 1.15`；落定软着陆挤压回弹 ~160ms。
- **旋转视角**：单指在棋盘空白处横向拖动即可旋转（灵敏度 `0.008 rad/px`，150px ≈ 69°）；托盘/HUD/弹窗为屏幕层不随棋盘转；旋转与拖子手势互斥（按下时按落点分流）。

### 3.5 合并 / 消除规则（M3-K · 顶层同色连通 + 整摞迁移）

- **PLACE（整组落入）**：拖一组棋子入空格 → 该格 `stack = group.tiles`（整组成为该格一摞，可混色），落点格作为本次合并的**锚 `C0`**。立刻触发 **`resolveBoard` 结算**。
- **MERGE（顶层同色连通合并 · flood-fill，M3-K 铁律）**：
  - **仅"最上层棋子同色且几何相邻"才触发合并**：某格属于颜色 `c` 的连通分量，当且仅当其**顶层**棋子颜色为 `c`——埋藏在堆叠内部的同色棋子**不参与**邻接判定（Hexa Sort 原版语义）。
  - 触发后，组件内除锚格外，其余格的**整摞棋子（含埋藏的异色）**逐片飞向锚格叠高，埋藏色随行且**保持底→顶顺序**。这正是用户要的：只有"看得见的顶层"决定谁能连；混色部分被"驮"着一起走。
  - **锚优先取刚落下的格 `C0`**（否则取棋子最多的格）。
  - **动画**：每个 tile 从源格原高度飞向锚格目标层，带弧线 hop（中段跃起），每片 ~240ms ease-out、片间错峰 ~110ms（一块一块摞上去）；逐片落定触发"咔哒"音效（音高随层高升调）+ 落地挤压回弹。
  - 全部到位后：各源格 `stack=[]`，锚格持有整摞（顶层仍为触发色 `c`）。
- **ELIMINATE（单格消除，M3-K）**：**某一格内同色棋子累计 ≥ `ELIMINATE_AT(10)`** 即消除该色（合并会把同顶层色收拢进一格，故只需单格判定；埋藏色在收拢/消除后同样计数）：
  - 该格 `stack` 移除该色全部棋子（粒子消散 + 高亮），`clearedTotal++`。
  - 分数：消除分 + 连击乘数（×1.2 / ×1.5 / ×2）；`clearedColors` 记录该色。
  - **将杀**：单关内 6 色各消除 ≥1 → 全屏 CHECKMATE（金闪 + 字样缩放入场 + 奖励）。
- **结算顺序**：`resolveBoard` 先尝试"顶层同色分散 → 整摞飞叠归拢"，再检查"某格同色 ≥10 → 消除"，循环直到稳定（一次只跑一个飞叠动画，结束后再触发下一步；消除后顶层变化可能引发新合并/连锁）。
- **不做**：三连消、跨色连锁、固定"将营"——这些都不是 Hexa Sort。

### 3.6 失败判定与救援（M3-F · 真正的失败态）

- **失败定义**：所有 `cells.stack.length > 0`（满格无空可放）→ `over='fail'`。
  - 注意：这是 Hexa Sort 的**真失败态**（不是旧模型的"死局=救援提示"）。
  - 失败遮罩：「格满失败，重开本关」+ 仅"重开"按钮（无 Game Over 战绩惩罚，不扣星）。
- **救援三件套**（失败前/卡住时仍可主动用）：
  - **洗牌**：重排托盘剩余棋子的颜色分配（按"所需色"加权）——免费冷却 30s 或激励视频。
  - **撤销**：回退最近一次成功放置（含合并/消除结果回滚）——每日限量 或激励视频。
  - **提示**：高亮一个能触发合并/消除的放置点——免费冷却 或激励视频。
- 满格但**仍有可消除合并对** → 系统自动尝试一次"链式合并演示"（不放置新子，只是把可合并的对合并/消除一次，给玩家腾格）；仍满则失败。
- **生成器不变式**：`spawnBias` 倾向刷"能合并进现有叠"的色，降低填满到死的概率（不保证）。

### 3.7 计分 / 连击 / 星级

- **基础分**：成功放置 1 组 +5×组大小（无合并发生时给个底分）；合并飞 1 片 +2（鼓励链式合并）；**消除 1 叠满 10 +100 × 连击乘数**；**将杀 +200**。
- **连击（combo）**：相邻两次消除间隔 < `COMBO_WINDOW=2.5s` → 乘数档位 ×1.2 / ×1.5 / ×2（连续 2 / 4 / 6 次）。
- **星级（鼓励重玩）**：按 `steps`（总操作数）与 `rescuesUsed`（救援次数）评 1–3 星，规则（实现于 `board.ts completeLevel`）：
  - `stepOk = steps ≤ starThresholds.steps`；`rescueOk = rescuesUsed ≤ starThresholds.rescues`
  - **3 星**：`stepOk && rescueOk`（步数达标 且 零救援）
  - **2 星**：`stepOk || rescueOk`（任一达标）
  - **1 星**：两者皆未达标（仅代表本关已通关）
  - 阈值随关卡生成，默认 `starThresholds = { steps: goal*3, rescues: 0 }`（见 §3.9）。
- **进度持久化**：本地存「已解锁最高关 / 总星数 / 最佳分」；云存档（可选，§5.6）跨设备同步。

### 3.10 难度参数与进阶机制（M3-J 已接入）

- **进阶机制**（随关卡解锁，写进 `mechanics`，由 `levels.ts` 程序化生成）：

  - `decoy` 诱饵子（第 14 关起，概率 0.12→0.18）：托盘小概率刷入**场外色**（不在本关 activeColors 池内的颜色）干扰规划；场外色彼此仍可连通合并，靠洗牌/撤销化解。第 41 关起 6 色全开、无场外色，自动关闭。

- **机制首次出现弹一次轻提示**（Toast 3s，写入存档 `tipShown` 去重，每次进关最多一条）。

### 3.12 边界规则与不变式（M3-K · 开发必须遵守）

1. 颜色 ↔ 类型 **1:1 绑定**，永不混用。
2. **棋盘格无颜色预设**——任意颜色都能放进任何空格（M3-F 铁律）。
3. **合并 = 几何邻接（`hexDistance === 1`）∧ 双方顶层同色**；合并是**自动触发**，无需玩家操作；触发后**整摞迁移**（埋藏色随行）。
4. 消除阈值 `ELIMINATE_AT = 10`（招牌数字，常量；后期可配）；判定单位是**单格内同色计数**。
5. **失败态**：满格且无可消除可能 → `over='fail'`（非旧模型的"救援提示"）。
6. 「将杀」仅在单关内 6 色各消除 ≥1 次触发，触发后清空已消除色集合。
7. 触摸判定半径放大 **1.15×** 防误触（§3.4）；落点命中在**棋盘平面坐标**（逆视角变换后）判定，视角不影响准确度。
8. **无内购**；失败仅"重开本关"，**无 Game Over 战绩惩罚**（守住免版号红线，第 6–7 章）。
9. **视角变换严格可逆**：`boardToScreen` / `screenToBoard` 互为逆变换；渲染层变换与数学换算必须同源（先旋转后沿屏幕竖直压缩 `TILT=0.8`）。

## 4. 视觉风格

### 4.1 整体调性（M3-K · 像素管线定稿）

**温暖、治愈、轻度复古 + 伪 3D 像素体素（voxel）感**。参考 Hexa Sort 的「奶油色 + 柔和马卡龙色」视觉语言，叠加国际象棋的棋味身份；用**有高的六边形像素饼（hex pie）**作为唯一图元——高径比 ≈ 0.36（扁饼）、明确顶面（"饼馅"）+ 侧壁单带（"饼皮"）+ 顶亮带 + 底暗带 + 落地投影。

**像素风三级保障（M3-K）**：① **全画面像素管线**——所有绘制以 1/2 缩放落到低分辨率离屏缓冲、最近邻放大上屏（`game.ts` `PIXEL=2`，矢量/渐变/文字统一变硬边像素块）；② **等宽字体栈**（`"Courier New", Consolas, monospace`，经管线放大即像素字）；③ **方角像素 UI**——按钮/托盘/Toast 一律 `fillRect` 直角 + 亮/暗双色描边斜面，无圆角无抗锯齿。

**立体棋盘（M3-K）**：棋盘以固定俯角压缩（`TILT=0.8`，纵向压扁 20% 呈俯视立体感）+ **空白处拖动旋转**（`viewAngle`，0.008 rad/px）；渲染按屏幕 y 远近排序（画布变换：先 rotate 后 scale，与 `boardToScreen/screenToBoard` 数学换算同源），前方棋堆遮挡后方，**转动视角即可看到原本被遮挡的棋格**。不做写实 3D、不引入 WebGL，保持 Canvas2D 自绘的零包体优势（见 §4.6.6）。六边形格间缝隙收窄（`rad = 0.95·size`，接近相切）。

- **伪 3D 像素体素块**（Canvas 自绘，见 §4.6.6）：每个棋子是一块「挤出六边形」——顶面（专属色 + 白描边 + 内高光环）+ 正面侧壁（加深同色）+ 落地投影，读作像素/体素立体感。
- 顶面中心绘制**国际象棋经典剪影**（专属色填充 + 白描边）：兵=圆头立柱、马=马头、象=尖顶带缝、车=城垛、后=王冠带点、王=顶珠王冠。
- 为避免宗教敏感，**「象/Bishop」采用中性尖顶造型，不出现明确宗教符号**；命名上游戏内统一用「象」而非「主教」。
- 颜色 ↔ 棋子类型 **1:1 绑定**（红=兵、蓝=马…），图标是「皮肤」，玩家看颜色即可。

#### 4.6.2 两条生产路线（决策：路线 A 为主）
- **路线 A（默认·推荐）**：所有图形用 Canvas2D 路径**在代码里矢量绘制**（`src/render/sprites.ts`）。优点：包体 ≈ 0、任意分辨率清晰、改色只改数值。代价：复杂造型需手写路径。
- **路线 B（美术上限）**：Figma / Illustrator 设计后导出 **PNG 精灵图（@2x/@3x）+ 图集 JSON**。优点：可上复杂渐变/纹理、绘制开销低。代价：占包体、需处理多分辨率。
- MVP 走 A；低端机性能吃紧或要更精致时，对棋子/特效部分切 B。

#### 4.6.3 设计工具与交付
- 设计稿：Figma（免费）画 1024×1024 基准画板，定坐标 / 配色 / 间距，作为代码绘制参考。
- 导出（仅路线 B）：PNG-8/24 压缩、单图 ≤ 50KB、合图集；JSON 记录帧坐标。
- 字体：用系统 `PingFang SC` / 默认，不打包字体文件（省包体且合规）。

#### 4.6.4 包体约束（硬指标）
- 主包 ≤ 4MB；美术资源（矢量代码或 PNG）均计入。路线 A 几乎免费，路线 B 需严格压缩并用 `game.json` 分包（主包 ≤ 4MB，总包 ≤ 20MB）。

#### 4.6.5 绘制规范（实现 checklist）
- 棋子饼：高径比 ≈ 0.5 的六边形挤出饼（更扁，贴合用户"再扁一些"要求），顶面 mid shade + 内嵌更亮 hex 内馅 + 外缘描边；侧壁单带含顶亮带/底暗带两条离散色；落地投影；顶面叠 `drawChessIcon` 棋子剪影。选中/拖起态放大 1.12×。
- 棋盘格：空格为浅奶油底盘 hex + 虚线轮廓（无颜色预设）；叠高时每片独立画饼向上错落叠加，顶片显棋子剪影与 `xN` 叠高数；消除时整叠 `scale→0 + alpha→0` 同步粒子爆裂。详见 §4.6.6 实现。
- 背景：奶油白竖直渐变 + 极淡暗角；底部托盘托架为半透明白面板。
- 命中区：绘制尺寸 = 逻辑尺寸，触摸判定半径放大 1.15× 防误触。
- 合规：象用中性尖顶，不出现十字/明确宗教符号；命名全用「象」。

#### 4.6.6 有高的六边形像素饼 · 渲染实现（M3-F 重写 · 2026-08-19）

> "像素不够像素、3D 不够 3D、要有高的饼"——M3-F 重构后的视觉实现依据，写进 `src/render/sprites.ts`。

- **单位图元 `drawHexTile3D(ctx, x, y, r, color, h)`**——一个有**高度 h ≈ r * 0.5** 的六边形**饼**（hex prism，"高径比 ≈ 0.5"，更扁），`(x,y)` = 顶面中心，`h` 向下挤出。
  - **顶面（"饼馅"）**：mid shade 平涂六边形 → 内嵌一个 `r*0.78` 的更亮 hex 作"内馅" → 顶面外缘 `shade(color,-30)` 描边作"饼皮外沿"。三段离散色，硬边无渐变。
  - **侧壁（"饼皮"）**：单条连续带（不再拆 3 面），颜色 `shade(color,-18)`；带内**顶部 1/3** 叠一条更亮色 `shade(color,-8)` 的窄横带（"饼皮上沿高光"），**底部 1/3** 叠一条更暗色 `shade(color,-32)` 的窄横带（"饼皮下沿阴影"）。**三条离散色带 = 像素体素 3D 的关键**（不再是平滑渐变）。
  - **落地投影**：顶面中心下方 `rgba(58,53,48,0.18)` 椭圆，硬边像素对齐。
  - 所有坐标 `Math.round`；任何 fillRect/stroke 不用抗锯齿快捷。
- **堆叠（cell.stack 渲染）**：每片独立画饼，`stack[j]` 顶面 y 偏移 `j * (r * 0.42)`（向上叠，带重合）；最顶片顶面叠 `drawChessIcon(ctx, type, r*0.42)` 显棋味身份。**视觉上每片都是有高的独立饼**，不融成一块。
- **空棋盘格**（cell.stack.length === 0）：浅奶油底盘 hex（`rgba(255,255,255,0.55)`）+ 虚线轮廓（`setLineDash([4,4])`，`shade(target,-20)`），**无颜色预设**——任意颜色都能进。
- **合并飞行棋子 `drawFlyingTile`**：飞行中的 tile 是完整饼（顶面+侧壁+投影），从源格 `lerp` 到目标格上空，`ease-out`，~180ms；与落定目标格的 `stack` 视觉同步增长。
- **消除动画**：达 10 的 cell 该色整叠饼 `scale 1→0` 同步 `globalAlpha 1→0`（~300ms ease-in），同时同色粒子爆裂；结束 `cell.stack` 移除该色（空则 `[]`）。
- **像素感来源（M3-K 三级保障）**：① 全画面 1/2 缩放离屏缓冲 + 最近邻放大（`game.ts` PIXEL=2，实测颜色突变 100% 落在偶数坐标）；② 等宽字体栈像素字；③ 方角 UI + 纯色块 + 硬边描边 + `Math.round` + 3 条离散色带，绝不用平滑渐变；读作**像素体素饼**而非写实 3D。
- **立体视角（M3-K）**：渲染层 `translate(中心) → scale(1, TILT=0.8) → rotate(viewAngle) → translate(回)`；格绘制按屏幕 y 升序（远→近）保证遮挡正确；`boardToScreen/screenToBoard` 与该变换严格互逆（落点命中在棋盘平面坐标判定）。
- **包体**：代码矢量直绘（路线 A），包体 ≈ 0。

#### 4.7 音效引擎（M3-D 已实现）

- **方案**：用 Web Audio API **实时合成**所有音效（`createAudioEngine` 见 `src/platform/audio.ts`），**不打包任何音频文件**——契合「主包 ≤4MB / 资源矢量直绘」约束，包体 0 增长。
- **平台适配**：浏览器用 `AudioContext`，微信小游戏用 `wx.createWebAudioContext()`，两者 API 一致；`Platform.audio` 由 `wx.ts` / `dom.ts` 注入，`board.ts` 通过 `attachAudio()` 绑定，缺省为静音 no-op 引擎（逻辑单测不受影响）。

- **静音**：跟随存档 `save.muted`，`attachAudio` 时同步；设置页可切换（预留）。

## 5. 技术架构

> ⚠️ 注意：本项目是**微信小游戏**，不是标准小程序。  
> 小游戏用 `game.js` 入口 + **Canvas2D 自行渲染**，**没有 WXML/WXSS/Page/setData**。  
> 已安装的 `wechat-miniprogram` skill 讲的是标准小程序框架，仅其「云开发 / 广告概念 / 网络域名 / 性能原则」对小游戏通用，其余（WXML 组件、setData、分包页面的写法）**不适用**。

### 5.1 框架选型（推荐）

**原生微信小游戏 + TypeScript + esbuild 打包**。

| 方案               | 优点                                    | 缺点              | 结论                |
| ---------------- | ------------------------------------- | --------------- | ----------------- |
| 原生 Canvas2D + TS | 零引擎依赖、包体最小（易控 ≤4MB）、完全可控、复用你已有的 TS 能力 | 需自研场景/输入/循环     | ✅ **采用**          |
| Cocos Creator    | 可视化编辑器、物理/动画现成                        | 学习其 API、包体更大、黑盒 | 备选（若后期要复杂动画/多端发行） |

### 5.2 工程结构

项目根 `game.js` / `game.json` / `project.config.json` 为小游戏入口与配置；`src/` 为 TypeScript 源码，`dist/` 为浏览器试玩构建，`test/` 为 Node 逻辑单测。

- **主包 ≤ 4MB**（资源尽量矢量直绘 / 压缩音频，避免大图）。
- 主循环 `requestAnimationFrame`，目标 **60fps**；粒子用对象池复用。
- `devicePixelRatio` 上限设 2–3，避免高分屏过度绘制。
- 不阻塞首屏：资源在 Menu 场景异步预加载。

### 5.6 存档、变现与社交（已实现骨架，M3-C）

> 所有平台能力集中在 `src/platform/` 下，业务层只依赖 `types.ts` 的抽象接口；在「未配置真实 ID / 非微信环境」下自动降级为 no-op 或本地兜底，**游戏逻辑与 UI 不感知差异**。

- **本地存档**（已实现，M2）：`platform.storageGet/Set` 抽象，`board.save` 存「已解锁最高关 / 星级 / 最佳分 / 静音」。
- **广告 `AdManager`**（`src/platform/monetize.ts`）：封装横幅 / 插屏 / 激励视频三件套。
  - 真实广告位 ID 写在 `AD_UNIT` 常量，**空字符串即安全 no-op**（不会报错、不弹广告）。
  - `game.ts` 中 `SHOW_BANNER=false`（横幅需预留底部空间，且须流量主开通后填 ID 再开）、`INTERSTITIAL_EVERY=3`（每 3 关弹一次插屏）。
- **分享 `ShareManager`**（裂变拉新，小游戏增长第一引擎）：`enableShare` 注册右上角菜单卡片（带 `query` 深链），`share` 主动调起；`board.ts` 工具栏新增「分享」黄色按钮触发。
- **云排行榜 `CloudLeaderboard`**：当前 `enabled=false`，走本地兜底（`submitScore`/`getRank` 读写本地列表）；配好 `wx.cloud` 环境后切真实云端即可。
- **启动深链**：`platform.launchQuery()` 读取 `?level=N`，`board.gotoLevel` 直接进入对应关卡（受已解锁进度限制）。

### 6.1 广告位设计

| --------- | ------------ | ------ | ----------------- |

### 6.2 变现前提

- 需先开通**微信流量主**：累计独立访客（UV）达到平台门槛（最新阈值以官方公示为准，**历史约需 UV 500+**；此前社区常见为千级）。**未达门槛前广告位不展示、无收益**，但代码已就绪，达标即开。
- 个人主体**可以**申请流量主（只要游戏跑起来、有量）。
- 不诱导分享、不强制看广告才能玩核心循环。

### 6.3 与版号的关系

- **只要不开内购，休闲益智类小游戏通常免版号**。
- 一旦想加「卖皮肤/体力/去广告」等付费，就必须走版号（企业+100万注册+网文证+8 个月起），个人/个体均无法自申。
- → 在达到稳定流量、想认真商业化前，**坚决不碰内购**。

## 7. 合规与上线

### 7.1 主体与账号（你当前阶段）

- **个人主体**（推荐你起步）：身份证 + 刷脸注册，0 元，能开发/发布/接广告。
- 类目选 **「游戏 / 休闲益智」**。
- 若后续个人备案受阻，再办**个体工商户**（网上可办、成本低）顺滑升级。

### 7.2 上线前置动作

1. 微信公众平台注册**小游戏**账号（注意选「小游戏」不是「小程序」）。
2. 完成**小游戏备案**（按平台指引提交，个人也需备案）。
3. 软著（建议）：自助或代理申请，约 1–2 月，保护 + 部分渠道要求。
4. 内容安全：棋子图标中性化、无血腥/赌博/真实金钱元素。
5. 提审：包体合规、无外链、无违规广告。

### 7.3 内容审核红线（务必避开）

- ❌ 宗教敏感符号（象/Bishop 用中性造型）。
- ❌ 血腥、暴力、赌博、真实货币投注。
- ❌ 诱导分享文案（「分享得奖励」类违规）。
- ❌ 外链跳转非微信域 / 未备案域名。

### 7.4 原创性与版权合规（模仿 ≠ 侵权）

- 玩法机制不受版权保护，借鉴 Hexa Sort 的「六边形拖拽排序」机制合法。
- 三处必须原创，否则会被下架：① 名称（不用 Hexa Sort / 他人 IP）；② 美术素材（自绘，不扒图）；③ 代码（从零自研，不反编译搬运）。
- 避免「换皮」：本作以国际象棋皮肤 + 将杀包装做差异化，具备独立品牌，符合平台原创导向。
- 平台有「名称保护库」与代码 / 美术技术比对，侵权会下架甚至拉黑主体；个人开发更应注意。
