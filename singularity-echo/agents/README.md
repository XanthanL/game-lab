# 沟通机制 · 五个会话怎么各干各的不打架

> 面向**每一个**参与会话。开工第一步就是读这个文件。
> 上游文档：`../AGENTS.md`（所有权与硬约束）。

---

## 0. 先记住这三句话

1. **会话之间没有消息通道。** 你不能 @ 别人，别人也看不见你的屏幕。唯一共享介质是**磁盘文件**。
2. **你不是实时的。** 你写下的请求，别人可能几小时后才看到。所以不要等回复 ——
   遇到阻塞就**记下来，换个能做的事**，或者明确停下来等人类同步。
3. **不要试图让两个会话写同一个文件。** 每个文件有且只有一个主人（见 §2）。

---

## 1. 工作区隔离（最重要，先做这个）

**绝对不要直接在 `E:\Code\game-lab` 里干活。**

五个会话共用一个工作目录会发生什么：你 `git add` 的时候别人也在 `git add`，
你 `commit` 的时候会把别人 staged 的半成品一起提交；有人 `checkout` 会掀掉别人的改动。
（这不是假想 —— 本项目已经出过一次：一个会话 staged 了文件，另一个会话 commit 时
把它未完成的移植代码一起带进了提交，最后靠 `reset --soft` 才撤回。）

每人一个 **git worktree**，各自独立的工作目录 + 各自的分支 + 各自的 index：

```powershell
# 由人类在 E:\Code\game-lab 里执行一次，建好五个工作区
cd E:\Code\game-lab
git worktree add ..\gl-a -b agent/a-gplay
git worktree add ..\gl-b -b agent/b-visual
git worktree add ..\gl-c -b agent/c-system
git worktree add ..\gl-d -b agent/d-lore
git worktree add ..\gl-e -b agent/e-quality
```

然后**每个会话的工作目录**是：

| 角色 | 工作目录 | 分支 |
|---|---|---|
| A 玩法 | `E:\gl-a` | `agent/a-gplay` |
| B 表现 | `E:\gl-b` | `agent/b-visual` |
| C 系统 | `E:\gl-c` | `agent/c-system` |
| D 内容 | `E:\gl-d` | `agent/d-lore` |
| E 质量 | `E:\gl-e` | `agent/e-quality` |

收工后由人类清理：`git worktree remove ..\gl-a`（加 `--force` 可强删）。

> 代价：每个 worktree 是一份完整检出，约 195 MB × 5 ≈ 1 GB。磁盘够就别省这个。

## 2. 角色分配（不要靠自领）

### 首选：人类在提示词里直接指定

```
你是角色 A（玩法）。工作目录 E:\gl-a。不用认领，直接开工。
```

**这是唯一零竞态的做法，推荐。**

### 为什么不推荐自领

`agents/` 在 git 里，而**每个 worktree 是独立的一份文件树** ——
你在 `E:\gl-a\...\agents\A-玩法.md` 里改成「已认领」，
`E:\gl-b` 里的那份仍然是「未认领」。五个会话看到的是五份互不可见的副本，
自领机制形同虚设。

### 兜底：真要自领，必须认领在主工作区

若坚持让会话自领，认领动作**只能**发生在主工作区这一份上（所有人唯一可见的拷贝）：

1. 读 `E:\Code\game-lab\singularity-echo\agents\` 下五张卡，找第一张 `状态: 未认领`
2. 改该行 → 写回（**只改这一行，别碰主工作区的其他任何文件**）
3. 复读一遍确认没被抢；被抢了就换下一张
4. 认领完立刻回自己的 worktree 干活，之后**所有改动都只在自己的 worktree 里**

**角色卡 = 你的锁 + 你的状态板 + 你的日记。** 只有你能写自己的卡；别人的卡只读。

> 日常进度写在你自己 worktree 的卡里即可。别人看到它的时机是**下一次合并**，
> 不是立刻 —— 这是并行开发的固有代价，接受它。

## 4. 日常沟通动作

### 每完成一步 → 更新自己的角色卡

角色卡里有 `## 进度` 区，追加一行：

```
16:20  新增敌型 Swarmling 挂进 EN_UNLOCK | 改了 sections: 敌型数据表, spawning | 进行中
```

**必须写清改了哪些分节** —— 这是别人和你预判合并冲突的唯一依据。

### 需要别人配合 → 写 `REQUESTS.md`

```
## 2026-09-14
- [ ] A→B：新敌型 Swarmling 需要一个新的绘制分支，数据流见 NOVA.debug('EN_UNLOCK.Swarmling')（A，16:30）
- [ ] B→C：设置面板新增「BGM 内存上限」下拉，请接入 OPTS 持久化（B，17:05）
```

- **只追加，不修改、不删除别人的行**（否则写冲突）
- 完成后由人类或请求方把 `[ ]` 改成 `[x]`，**不要删行**（留痕）
- 被请求方**不会自动收到通知**。请求真正的用途是给下一次合并的人类一张清单

### 发现共享事实 → 更新 `BASELINE.md`

任何量出来的、别人也会引用的数字（帧耗时、内存、数量统计）写进 `BASELINE.md`。
这样避免五个会话各量一遍、还量出五个不同的数。**只有 E 能改这张表**，其他人发现了就写进 REQUESTS。

### 详细过程与踩坑 → 追加 `../DEV-PLAN.md`

它本来就是这个用途（每天一行，含回退点路径与截图位置）。

## 5. 同步节奏（人类主导）

会话之间**不会自动同步**。建议：

- **每个会话独立推进**，不等待别的会话
- **人类每天合并一次**：按 D → E → A → B → C 的顺序（先合零冲突的）
- 合并后各会话 `git merge main` 或 rebase 到最新再继续
- 冲突判不了的（比如两个人都动了 `boot`）—— **让后合并的一方 rebase 重做，不要手工缝合**

## 6. 明确的禁止事项

- ❌ 在 `E:\Code\game-lab` 主工作区改任何东西
- ❌ 写别人的角色卡
- ❌ 删改 `REQUESTS.md` 里别人的行
- ❌ 全局重排 / 格式化 / 批量替换 `index.html`（会让所有人 diff 同时冲突）
- ❌ 顺手改不在你所有权里的分节（看见了也当作没看见，记进 REQUESTS 就好）
- ❌ 提交信息写 `update`（写 `fix(域): xxx` / `feat(域): xxx`）
- ❌ 等着别的会话回复你 —— 记下来，继续做下一件事
